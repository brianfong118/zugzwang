# Design

Decisions and their reasons. When a decision changes, mark the old one superseded rather than deleting it.

## Toolchain
- C++20, CMake, Ninja. GCC/Clang via MSYS2 UCRT64 on Windows; GCC on Linux CI. One compiler family means one flag set shared by dev machine and CI: `-march=native` on top of CMake's `-O3` in Release; `-fsanitize=address,undefined` in Debug on Linux (MinGW GCC lacks ASan, so CI runs the sanitizers).
- `<bit>` over intrinsics: portable, identical codegen at `-O3`.
- Flags live on one `zugzwang_options` INTERFACE target that every executable links, so the engine and the tests are always built the same way.
- Engine sources compile once into a static library `zugzwang_core`; `main.cpp` holds only the entry point. The test binary links the same objects the engine ships, and supplies its own `main` so it can run `attacks::init()` before Catch2 starts.
- MinGW builds link `-static`. The engine binary is copied next to lichess-bot and must not depend on whichever MSYS2 runtime DLLs are on PATH; a toolchain newer than the installed `libstdc++-6.dll` otherwise fails at load with `STATUS_ENTRYPOINT_NOT_FOUND`.
- Catch2 via FetchContent. Perft is the primary correctness check; unit tests cover FEN round-trips, UCI parsing and eval symmetry (mirrored position, negated score).
- CI builds Release and Debug on every push and runs the tests under sanitizers, excluding `[slow]` perft cases. Debug adds `-fno-sanitize-recover=all`, because UBSan otherwise only prints a message and exits 0, and CI could never fail on undefined behaviour.
- CI's build job times out after 20 minutes. A broken time or stop limit makes a test hang rather than fail, and GitHub's default timeout is six hours.
- CI pins `clang-format` to 21.1.8. Versions lay out the same code differently, so an unpinned runner fails code that is correctly formatted locally. Update the pin when the local version changes.

## Board
- Bitboards: one per piece type per colour, two colour occupancies, plus a 64-entry mailbox so piece-at-square is a lookup, not a 12-bitboard scan.
- Magic bitboards for sliders, magics found at startup. Avoids committing a table; measured cost is ~200 ms per process with an untuned seed (rooks need ~1M candidate multipliers, bishops ~80k). Per-rank tuned seeds would cut that to ~10 ms if startup time ever matters; it does not for lichess-bot or SPRT. PEXT can be added behind an `#ifdef` later.
- Leaper tables (pawn, knight, king) are `constexpr`: zero startup cost and testable with `STATIC_REQUIRE`. Slider tables cannot be, since the random magic search exceeds compile-time evaluation limits.
- `attacks::init()` is explicit, called from `main()` and the test main, rather than a static initialiser. Nothing that runs during static initialisation can then depend on the tables being ready.
- Slider lookups stay inline in the header (`Magic` table declared `extern`) because they sit on the move-generation hot path; the search that fills the tables lives in the `.cpp`.
- One fixed-seed SplitMix64 PRNG (`prng.h`) serves magic search and Zobrist keys: the same magics and hashes every run, so bench and hash-dependent behaviour are reproducible.
- `kCastlingRules` is the one description of castling geometry. Move generation, FEN validation, rights loss and the rook's move all read it, so they cannot disagree.
- Make/unmake with an undo stack rather than copy-make: cheaper once state grows to include NNUE accumulators.
- The undo stack is a `std::vector` in `Position`, reserved to 1024 entries. Any game length fits with no overflow handling, `Position` stays small, and `make` allocates only if a game outgrows the reservation. Each entry keeps the position's key, which repetition detection will walk. A copy does not inherit the reservation, so `search` calls `reserveHistory(kMaxPly)` before it starts. `make` then never allocates mid-search, even on the copy the search thread works on.
- Zobrist hash updated incrementally from day 1: needed for repetition detection in v1 and the TT in v1.1.
- 16-bit moves (from, to, 4 flag bits for promotion/castling/en passant). Compact in move lists and TT entries. No capture or double-push flag: the mailbox gives the captured piece and the distance moved gives the double push.
- Pseudo-legal generation, legality checked in make. Simpler than legal generation; the wasted work is small. `make` returns false and restores the position itself on an illegal move, so no caller can forget the cleanup. The castling attack rules live there too, so legality has one home.
- `generateMoves` produces every move. `generateNoisy`, added for quiescence in v1.0, produces the moves that change material: captures, en passant and queen promotions. Stockfish's capture generator likewise includes queen promotions. Underpromotions are left out. One beats a queen only by giving a knight check or avoiding stalemate, and quiescence sees neither checks nor stalemate. Both lists come from one template, so they cannot disagree on what counts as a capture. The full list keeps its order, so the bench is unchanged.
- `MoveList` is a fixed array, so generation never allocates, and `Move`'s trivial default constructor means declaring a list writes nothing. Capacity is 415, a proven bound, rather than the conventional 256. 218 is the known maximum for legal positions, but `fromFen` also accepts positions no game can reach, and a search found a 28-piece FEN with 267 pseudo-legal moves. `fromFen` therefore caps each side at 16 pieces, and the bound follows: 15 queens of 27 moves, plus a king's 8 and 2 castles.
- `Position::fromFen` returns `std::optional` rather than throwing: the UCI loop must survive a bad `position` command, and the codebase has no exceptions. Validation is structural: at most six fields, so a mistyped `moves` keyword cannot be silently dropped; eight ranks of eight; exactly one king per side; at most sixteen pieces per side; no pawns on the back ranks; an en passant square on the correct rank, empty, with the pushed pawn in front of it and that pawn's origin empty; and clocks of at most 1,000,000, so `make` cannot overflow them. One check goes beyond structure and supersedes the earlier "structural only" rule: the side not to move must not be in check, which also rejects adjacent kings. Otherwise pseudo-legal generation would offer a king capture, and `kingSquare` is undefined with no king on the board. `fromFen` therefore needs `attacks::init()` to have run. It is also the only way to create a `Position`, so every `Position` has two kings. A castling right whose king or rook is not on its home square is dropped rather than rejected (as Stockfish does), so the board guarantees the invariant "right set ⇒ king and rook at home" and castling generation need not re-check it.
- The en passant square is stored and printed as given, but hashed only when a pawn of the side to move attacks it. FIDE repetition compares the set of legal moves, so an uncapturable ep square must not distinguish two otherwise identical positions. Pins are ignored: a pinned pawn still counts, which can only miss a repetition in that rare case, and a full legality check is not worth running on every double push.
- Zobrist keys are a `constexpr` table generated from the fixed-seed PRNG; the sixteen castling keys are indexed by the rights mask so an update is `key ^= castling[old] ^ castling[new]`. Piece placement updates the key incrementally from the first `putPiece`; `computeKey()` recomputes from scratch and exists only to check the incremental key in tests. `unmake` restores the key from the undo entry rather than reversing the XORs. `putPiece` and `removePiece` still hash during `unmake`, and the result is overwritten. Avoiding that gains 2-4% in perft but needs a second pair of helpers, which is not worth it before search exists to profile.

## Search
- v0.2: iterative deepening and negamax alpha-beta on a material-only eval. This supersedes the original plan to start search in v1. v0.2 already needed `go`, `stop` and `bench`, so it needed a search, and a placeholder that played random moves would have been thrown away.
- v1: quiescence (captures only, stand-pat), MVV-LVA ordering. Quiescence is in v1 because material-only eval without it hangs pieces at the horizon and the bot would look broken rather than weak.
- MVV-LVA scores each move once as 8 × (victim + 1) − attacker, using the piece type indices. 8 exceeds every attacker index, so the most valuable victim always comes first and the cheapest attacker only breaks ties. That is the order of the Chess Programming Wiki's MVV-LVA table. A queen promotion adds a queen capture's score. Every capture and queen promotion is placed above every other move, which the killer and history entries below then order. Stockfish replaces the attacker term with a capture history learned during search, an extension of the quiet history below.
- Moves are handed out by selection: each step swaps the best remaining move forward. A cutoff usually comes within the first few moves, so most of a list is never ordered. `std::stable_sort` would read more simply, but it may allocate, and nothing on the search path allocates. Ties go to the earliest move, so the order, and with it the bench, is the same on every run and build.
- Quiescence replaces the static eval at depth 0. The side to move may stand pat on the static eval, because it is never forced to capture. Otherwise it searches noisy moves in MVV-LVA order with fail-soft alpha-beta, and it does not extend the PV. It stands pat even in check, as in the Chess Programming Wiki's basic version, so it misses a mate that happens inside quiescence. Stockfish searches every evasion in check instead; the v1.x check extensions narrow the gap more cheaply. (Superseded in v1.x: quiescence skips captures that lose material by SEE; see SEE below.)
- Negamax hands over to quiescence at depth 0 before counting the node, so each leaf counts once. Quiescence then checks for draws itself, as Stockfish's does, because the move into the leaf may have repeated the position. Every later quiescence move is a capture or a pawn move, which resets the halfmove clock, so after the first ply the check costs one comparison. At `ply >= kMaxPly` it returns the static eval, also as Stockfish does: depth no longer bounds the ply, and the search's history reservation assumes no line runs past `kMaxPly` plies.
- A test checks the search against plain minimax, with an unpruned quiescence at the leaves. It runs at depth 4 on endgames and a mate in two. Alpha-beta and move ordering must not change the score, so a selection bug that skips or repeats a move shows up there. Unpruned quiescence is exponential in middlegames, passing 200M nodes on Kiwipete at depth 1, so the middlegame positions are covered by bench and the other search tests instead. The test holds only while every pruning step is exact; null-move pruning and LMR in v1.x will end it. (Superseded in v1.x: the test now runs with forward pruning switched off; see null-move pruning below. The switch is now `selective` and turns off LMR too, and SEE pruning in quiescence.) The transposition table keeps it exact. A hit needs an entry at least as deep as the node, and at depth 4 a position can recur at another ply only at the leaves, which never probe.
- v1.x: transposition table, killer and history ordering, null-move pruning, late move reductions, check extensions, aspiration windows. One change per SPRT.
- v1.x transposition table: one 16-byte entry per slot (full 64-bit key, score, depth, bound), a power-of-two count indexed by the key's low bits, and every store replaces the slot. Storing the full key means two positions are confused only if all 64 bits match, and 16 bytes puts four entries in a cache line, so a probe costs at most one miss. A move is not stored yet: TT move ordering and a bucketed replacement scheme are a later roadmap item, so this SPRT measures cutoffs alone.
- The table is 64 MB, fixed. A blitz move on Lichess searches for several seconds, tens of millions of nodes, which would overwrite Stockfish's 16 MB default several times over. An SPRT runs 22 engines, about 1.4 GB, which fits. There is no `Hash` option, since nothing sets one.
- A hit at least as deep as the node ends it only when its bound settles the node: a lower bound at or above beta, or an upper bound at or below alpha. An exact score inside the window is searched again, as at Stockfish's PV nodes. "Non-PV nodes only" cannot be the rule here, because without null-window searches almost every node has a wide window. A node whose score lands inside its window is on the PV, so no PV node is cut and the bottom-up PV stays whole. The root never probes, so it always returns a move, which matters once aspiration windows narrow it.
- Every completed node stores its score, as a lower bound when it failed high, an upper bound when it failed low and exact otherwise. A stopped node returns before storing, so an interrupted search leaves no partial result. Quiescence neither probes nor stores.
- Mate scores are stored as the distance from the node and read back as the distance from the root, so a mate found at ply 2 and reused at ply 4, or in the next move's search, keeps its true distance. A sweep of 135 short mates searched with and without the conversion found no difference at the root, because cutoffs only use out-of-window bounds, so `scoreToTt` and `scoreFromTt` are tested directly.
- The table is passed to `search` rather than kept as a global. `Uci` owns the engine's table and keeps it between moves, since the next search reuses much of the last; `ucinewgame` stops any search and clears it. `bench` builds its own, so its node count does not depend on earlier searches, and keeps it across its ten positions, as Stockfish's bench does. Tests give every search a fresh table, so no test depends on another.
- Repetition and fifty-move draws depend on the path and the halfmove clock, and neither is in the key, so a score shaped by a draw can be reused where the draw does not apply. Most engines accept this graph-history interaction, and so does this one. Draws are checked before the probe, so a position that is itself a draw is never scored from the table.
- The table cut bench nodes by 22%, and cost about 3% of nps on lookups, pinned to one core on the PC. It passed SPRT at +101 Elo.
- v1.x killer and history ordering. A quiet move is one that is neither a capture nor a queen promotion, the moves quiescence never searches; non-capturing underpromotions count as quiet. Quiet moves follow every capture: first the two killers for the node's ply, newest first, then the rest by history score. Before this, quiet moves were tried in generation order.
- A killer is a quiet move that caused a beta cutoff at the same ply elsewhere in the tree. Sibling positions often share a refutation, such as a threat the opponent ignored. Killers are matched against the generated list rather than played directly, so a killer that is not pseudo-legal in this position is never tried and needs no legality check. Two slots, as in most engines, keep the previous refutation when a new one arrives. The empty slots hold a1a1, which no generated move equals.
- History is a butterfly table, indexed by side to move, from square and to square, as Stockfish's `ButterflyHistory` is. When a quiet move cuts off, it gains depth², since a cutoff with more depth left prunes a larger subtree. Every quiet move tried before it at that node loses the same amount (the history malus), because each was searched and failed to refute. Only quiet cutoffs update it; captures are already ordered by MVV-LVA.
- History updates use the gravity formula `h += bonus − h × |bonus| / 16384`. An update shrinks as the entry nears ±16384 in its direction, so with |bonus| ≤ 16384 the entry never leaves that range. The table needs no periodic halving and cannot overflow, and recent cutoffs outweigh old ones. The largest bonus is 128² = 16384, and a `static_assert` ties `kMaxPly` to that bound.
- The scores share one `int` array, so the existing selection orders every band: history within ±16384, the second and first killer at 16385 and 16386, and captures at 16387 plus MVV-LVA. Quiescence sees only noisy moves, so its order is unchanged.
- Killers and history belong to the `Searcher` and start empty on every `go`, unlike the transposition table, which is kept between moves. A fresh start makes each search independent of the game before it, and the table already carries most of what is worth reusing. Stockfish keeps its histories between moves; that is a candidate for its own SPRT. Underpromotions to the same square share a history entry, which matters little because they almost never cut off.
- Killers and history cut bench nodes by 37%, and cost about 2–3% of nps, pinned to one core on the PC. It passed SPRT at +173 Elo, as large as it is because quiet moves had no ordering at all and the table stores no move yet.
- v1.x null-move pruning. At a node that looks likely to fail high, the side to move first passes, and the opponent's reply is searched to a reduced depth with a null window at beta. If even that free move cannot bring the score below beta, the node returns without searching its moves. This rests on the null-move observation: in almost every position some move is better than passing, so a pass that still reaches beta suggests that a real move would too.
- It is not tried at the root, which must return a move, or in check, where passing is illegal. It is not tried straight after another null move, because a second pass gives back the same position with the same side to move, so it would only repeat the first search at less depth. It is not tried when the side to move has only king and pawns. There zugzwang is common, passing may well be the best move, and the observation fails. It needs depth 2 or more and a static eval of at least beta. The eval is computed only once the cheaper conditions hold, since evaluation costs about 40% of nps.
- The eval condition aims the null search at nodes that are likely to fail high, which is all it can show. Since the eval never comes near a mate score, it also rules out a beta at or above mate, including the root window's infinite beta. Depth 1 is excluded because there the null search is quiescence, and so is the search after the first real move. A null cutoff swaps one quiescence search for another, and a failed null search adds one. Over the ten bench positions searched to depth 8, allowing depth 1 cost 10.6M nodes, against 7.4M from depth 2 and 7.9M from depth 3. At depth 10, depth 2 needed 67.6M nodes and depth 3 needed 78.1M.
- The rule in PVS engines is "non-PV nodes only", where a PV node is one with an open window. This search has no null-window searches, so almost every node has an open window, and the rule would switch null-move pruning off, as with the transposition table above. What the rule protects is the PV, and here that holds by construction. A null cutoff only ever returns a fail high, outside the window, so no node whose score lands inside its window is cut, and the root is excluded. The eval condition does the rest of the rule's job: it keeps the attempts to expected cut nodes, which in a PVS engine is what "non-PV" selects. A null cutoff can still be wrong, through zugzwang or a threat beyond the reduced depth, exactly as at a non-PV node in a PVS engine.
- The reduction is R = 3 + depth/4, and the null search runs to depth − 1 − R, dropping into quiescence at 0 or below, so until depth 6 it is quiescence alone. This is close to the depth term of Stockfish's formula around version 10, (823 + 67 × depth) / 256 ≈ 3.2 + depth/3.8, without its eval term. At depth 10 on the bench positions, the classic fixed R = 2 needed 92.8M nodes, against 67.6M for this R and 59.0M for 3 + depth/3. A larger R always saves nodes at a fixed depth, at some cost in accuracy, so the node counts cannot settle R. Tuning it is a candidate for its own SPRT.
- A mate score from the null search is replaced by beta. The line behind it begins with a pass, which is not a legal move, so the mate may not exist with a real move, and its distance counts the pass. Returned as it is, it would enter the table and pass up the tree as a proven mate, where it could be reported or chased. The pass still shows that the node reaches beta, so beta is safe to return. Older Stockfish versions clamped the same way; recent ones skip the cutoff instead. Other scores are returned as they are, fail-soft.
- A null cutoff returns without storing in the table. Its bound comes from a shallower search behind a pass, so storing it at the node's depth would claim more than was searched. Stockfish's null cutoff does not store either. The ancestors still store bounds that include it.
- `Position::makeNull` flips the side to move and its key, and clears the en passant square. If that square was hashed, its key comes out first, while the side to move is still the one that could capture. The capture belonged to the side passing, and no double push has just been played for the other side. Pieces and castling rights are unchanged. The halfmove clock counts the pass, as Stockfish's does, since a pass is neither a capture nor a pawn move, so a null search still sees a fifty-move draw. The null move pushes an undo entry like a real move, so the history keeps one entry per ply, and `unmakeNull` restores the key, the counters and the en passant square from it. No `Move` value stands for the pass, so no move list or table entry can hold one.
- A repeat that spans a pass is not a real repetition. While one side passes, the other can recreate an earlier position, for example by moving a knight out and back while the opponent passes twice. A draw score there would let a null search return a false draw. `Position` therefore counts `pliesFromNull`, the history entries since setup or the last pass, as Stockfish's `StateInfo` does. `isDraw` scans back no further than the smaller of it and the halfmove clock, so no scan crosses a pass, while a repeat after the pass still counts. The count never exceeds the recorded history, so it replaces the scan's old bound at the history's length. A first version reset the halfmove clock on a pass instead, which needed no new state. The code review rejected it, because it also hid fifty-move draws inside null searches. A null cutoff near the limit could then claim a win where every real line draws, which matters most in a won endgame that is running out of moves. The extra count makes each undo entry 24 bytes instead of 16, and bench nps did not measurably change.
- `SearchLimits::forwardPruning`, on by default, switches null-move pruning off, and LMR will join it. The minimax test runs with it off, so it still checks that alpha-beta, move ordering and the table are exact. Those are the parts aspiration windows and TT move ordering will change. A second test checks that the switch changes the search, so a switch that silently stopped working could not leave the minimax test passing with pruning on. A third checks that a blocked king-and-pawn ending is searched identically either way. The flag lives in `SearchLimits`, which already carries everything a `go` passes to the search, rather than in a new options struct. (Superseded in v1.x: renamed `selective` when LMR joined it; see late move reductions below.)
- Null-move pruning cut bench nodes by 27%, and nps was unchanged within noise, unpinned on the PC. The bench depth of 5 understates the gain, because every null search there is quiescence. Over the bench positions searched to depth 8, it needed 7.4M nodes against the killer and history build's 43.1M, and 0.9 s against 5.3 s. On Kiwipete at depth 5 it searches more nodes than without, 243k against 207k. Quiescence after a pass is expensive there, because every capture is still available and quiescence prunes none, so pruning losing captures by SEE would make null searches cheaper. It passed SPRT at +109 Elo.
- v1.x late move reductions (LMR). Once a node's first few moves have been searched, a later quiet move is first searched to a reduced depth with a null window at alpha. Only if that search beats alpha is the move searched again at full depth with the node's own window. This rests on move ordering: after the captures, the killers and the best history moves, a move rarely beats alpha, so most late moves fail low at the reduced depth and are never searched in full.
- LMR does not need PVS. The reduced search only has to answer whether the move can beat alpha, and a null window (alpha, alpha + 1) answers that at the lowest cost without PVS. A move that beats it goes straight to a full-depth, full-window search, which is what every move cost before LMR. In a PVS engine that re-search is itself a full-depth null-window search, widened only if it also fails high, so PVS would make re-searches cheaper. That is a separate change, and LMR does not depend on it.
- A move is reduced only when all of these hold: the node has depth 3 or more, the side to move is not in check, the move is quiet, it is not one of the node's two killers, it does not give check, and it is the fourth legal move or later. The count is of legal moves, since `make` rejects illegal ones before they are counted. The same rules apply at the root, as in Stockfish and Ethereal.
- Captures and queen promotions, the noisy moves, are never reduced. They change material, which a shallower search is most likely to misjudge. Engines that reduce captures rank them by SEE or a capture history first, and this one has neither, so it cannot tell a losing capture from a winning one. Non-capturing underpromotions count as quiet, as they do for killers and history, and are reduced. A knight underpromotion that gives check is exempt as a check.
- Killers refuted a sibling, so they are the quiet moves likeliest to cut off. Older Stockfish versions reduced them a ply less than other quiet moves; exempting them is the simpler rule. In check, every move is an evasion, there are few of them, and history knows nothing about which evasion is best, so a late one is no less likely to be right. A checking move is forcing, and a mating attack is a run of checks, so reducing checks would delay mates the most. Whether a move gives check is read from `Position::inCheck` after `make`, and only once every cheaper condition holds.
- The first three legal moves are never reduced. Stockfish and Ethereal reduce from the second move, but they try the TT move first. This table stores no move yet, so the best move is less often first. Captures and killers are exempt anyway, so in a quiet position the rule mostly spares the best history move. This is worth revisiting once TT move ordering lands.
- The minimum depth is 3. At depth 2 the reduced search would be quiescence, which searches no quiet reply at all, so it would test the move only against standing pat and captures. A reduction is at most depth − 2, so the reduced search always keeps at least one full ply.
- The reduction is R = ⌊0.75 + ln(depth) × ln(move number) / 2.25⌋, Ethereal's formula, capped at depth − 2. The reduced search runs to depth − 1 − R. A deeper node has more depth to spare, and a later move is less likely to be best, so R grows with both, but logarithmically, so it grows slowly. Where LMR applies, R is at least 1. It is 1 at depth 3, 2 at depth 6 for the 10th move, 3 at depth 10 for the 20th, and 5 at depth 20 for the 40th. A constant R of 1 or 2 is the classic alternative, but the table is the common practice, and its slow growth suits a search without PVS, where every re-search costs a full window. Its constants are tuned for Ethereal, and tuning them here is a candidate for its own SPRT.
- R comes from a 64 × 64 table indexed by depth and move number, each capped at 63, so no `log` runs during search. `std::log` is not `constexpr` in C++20, so the table is built by a lambda when the program starts. It is a namespace-scope constant rather than a function-local static, so a lookup costs no initialisation guard.
- A reduced search that fails low is accepted. Its fail-soft score is an upper bound from a shallower search, and it counts towards the node's best score like any other fail-low. Every move that raises alpha has therefore been searched at full depth, so the PV, every cutoff, and the killer and history updates they make all come from full-depth searches. At a node whose window is already null, the two windows are the same, and the re-search differs only in depth.
- Null-move pruning and LMR complement each other. Null-move pruning cuts nodes that look likely to fail high, and LMR shortens the late moves of nodes that are likely to fail low. A line can be shortened by both, and as in other engines no rule prevents it. Inside a null search, LMR runs as at any other node. A reduced search is a null-window search, so its nodes have beta = alpha + 1, and the null move's eval condition holds there more often.
- The transposition table needs no new rule. A node stores its result at its own depth even when some of its moves were reduced, as in every engine with LMR, since the reductions are part of how a node of that depth is searched. A reduced child stores at its reduced depth, so a later probe at full depth cannot cut off on that entry. Bounds from null-window searches are stored like any other bound.
- A mate score that raises alpha has always been confirmed by a full-depth search. A reduction searches a line less deeply but never skips a reply, so a mate that a reduced search finds against the side to move is real within its horizon, and it is kept as a fail-low bound like any other score. The cost is time. When the first move of a mate is a late quiet move, the mate shows only once the reduced search reaches it. In the mate-in-two test, Kb6 is ordered late among 21 root moves, so its mate appears at depth 7 instead of 4, and the test now searches to depth 7. Checks and evasions are never reduced, so a mate made of checks is not delayed.
- `SearchLimits::forwardPruning` is renamed `selective`, because LMR reduces rather than prunes, and check extensions will need the minimax test to switch them off too. The minimax test runs with it off, as before. The king-and-pawn test now runs at depth 3, where LMR cannot act: the root has three legal moves, and every other node has depth 2 or less. With the king-and-pawn rule removed, that search uses 78 nodes instead of 82, so the test still catches it. The start-position test, which either technique alone could pass, is replaced by one test per technique, so neither can stop working unnoticed. The LMR test searches the same ending to depth 6, where null-move pruning never runs. The null-move test searches an opening position to depth 3 with the side to move in check, where LMR cannot act: the root is in check, and every other node has depth 2 or less. (Superseded in v1.x: SEE pruning acts in that position, so the test now uses a lone king; see SEE below.)
- LMR cut bench nodes by 68%, from 429,328 to 138,168, with nps 8.1M against 8.5M, pinned to one core on the PC. Over the bench positions to depth 8, it needed 1.47M nodes against the null-move build's 7.41M, and 0.19 s against 0.89 s. To depth 10, it needed 6.47M against 68.6M, and 0.80 s against 8.28 s. It reaches depth 12 in 4.0 s, half the time the null-move build needs for depth 10. nps at depth 10 is 3% lower, 8.06M against 8.28M. That was not profiled; the likely costs are the check test after `make` and a larger share of full-width nodes, which cost more than quiescence nodes. It passed SPRT at +102 Elo.
- v1.x check extensions are deferred until SEE, and the work is parked on the `check-extensions` branch with its full reasoning. The classic form extends every node in check by one ply. With checks and evasions still exempt from LMR, it failed SPRT at −29.6 Elo. Every run of checks was searched at full width, and bench time to depth 11 doubled. Reducing late checks and evasions brought it to −3.2 ± 8.1 Elo over 4,000 games, with no result. Most of the cost is checks that lose material, such as a rook checking from a square where it is simply taken. Excluding those needs SEE, so the extension waits for it and will move to the checking move, where SEE can judge it.
- v1.x static exchange evaluation (SEE). It plays out the captures on one square, each side recapturing with its cheapest attacker and stopping when that pays, and reports whether the side to move comes out ahead. Check extensions need it to skip checks that lose material, and quiescence, its first use, needs it to skip losing captures. On its own it changes no move, so it is measured through that first use.
- It answers a threshold question, `seeGe(pos, m, threshold)`, as Stockfish's `see_ge` and Ethereal's `staticExchangeEvaluation` do, rather than returning the exchange's value from a swap list. Every use compares against a margin. The threshold form also settles most captures without looking at attackers: a victim worth less than the threshold fails at once, and a capture that stays ahead even if the mover is then lost passes at once, so against quiescence's threshold of 0, PxN, NxN and RxQ never generate attackers.
- The loop keeps one balance from the point of view of the side that just captured, assuming it loses that piece next, and negates it each turn, as Ethereal does. The side to recapture is always the one that is behind if it stops. It holds after the first capture, or the threshold test would have settled the move. It holds after every later one too: the loop goes on only when the capturer would fall behind by losing its new piece, and until it loses it, the capturer is ahead. So that side recaptures whenever it can, and the exchange ends when it has no attacker left, or when the side that just captured stays ahead even after losing its piece. Whoever is left to recapture has lost. The −1 in each negation makes the two sides' tests complementary, so a balance of exactly the threshold counts for the side that made the move.
- Pieces leave a local occupancy as they capture, and every attacker is recomputed from that occupancy after each capture, which picks up a slider that was standing behind the piece that just left. Stockfish adds only the sliders a given piece type can uncover. Recomputing everything is simpler and costs two magic lookups and four table lookups per capture, and exchanges are short. `Position::isAttacked` cannot serve, because it answers for one colour against the real board, so SEE has its own attackers-to-square function.
- Values are the classic 100, 300, 300, 500 and 900, not PeSTO's. PeSTO's bishop is worth 28 more than its knight in the middlegame, so a bishop taking a knight defended by a pawn would count as losing, and quiescence would skip an even trade. The king counts 0, since a legal exchange never captures it. A king that captures onto a square the other side still attacks would have made an illegal move, so that side is treated as having had no capture. When the king makes the first capture, SEE passes it without looking further; if the victim was defended, the move is illegal, and `make` rejects it after SEE, as it rejects any illegal move.
- It ignores pins, so a pinned piece may recapture, as in basic swap-list SEEs. Stockfish checks pins, which needs pin and blocker data this engine does not keep. Checks, and anything beyond the one square, are ignored too. Castling, en passant and promotions count as 0, as Stockfish does. En passant takes a pawn from a square other than the target, and a promotion's worth depends on whether the new piece survives. Both pass a threshold of 0, so quiescence still searches them. SEE has its own module because check extensions, and later move ordering, will use it too.
- Quiescence skips any capture with SEE below 0, before making it, so a skipped capture costs no make or unmake. A capture that loses the exchange on its square leaves the side to move worse than standing pat, unless it wins something elsewhere, such as a discovered attack, which quiescence would rarely find anyway. Threshold 0 is the classic form; Stockfish prunes against a small negative margin, which is a tuning question for its own SPRT. In check, quiescence still stands pat, so nothing about checks changes. The pruning is inexact, so `SearchLimits::selective` switches it off, and the minimax test still compares against an unpruned quiescence.
- The SEE tests each pin an exact value: `seeGe` holds at it and fails one above it. They cover an unanswered capture, a defended pawn, even minor-piece trades, a rook behind the capturing rook, a rook behind the recapturing rook, a pawn uncovering a bishop, the king's recapture onto an attacked and an unattacked square, a quiet move onto an attacked square, en passant and promotion. Four mutants each fail at least one: no attacker update during the exchange, the mover's square left occupied, no king rule, and no −1. The quiescence test searches Kiwipete to depth 1, where null-move pruning, which needs depth 2 below the root, and LMR, which needs depth 3, cannot act. It visits fewer nodes with the switch on than off.
- The null-move test needed a new position, since SEE pruning acted in the old one and the test passed with null-move pruning switched off. None of the 12,714 positions from the check-extension search, 400 book positions and every position one move after them, had null-move pruning as its only selective step, because quiescence nearly always finds a losing capture. A lone king in check rules the others out by construction. The king's captures are never pruned, the other side has nothing to capture, the root is in check, so LMR skips it, and every other node has depth 2 or less. The test uses a rook checking a lone king: 114 nodes against 124, and 124 with null-move pruning off.
- SEE pruning cut bench nodes by 37%, from 15,055,075 to 9,524,360, with nps 6.76M against 8.01M, pinned to one core on the PC. Time to depth 11 fell from 1.88 s to 1.39 s, and no bench position got slower. That was not profiled; the likely costs of the 16% lower nps are SEE's attacker generation on captures of a cheaper piece, and a larger share of full-width nodes, which cost more than quiescence nodes.
- The SPRT against the LMR build passed: +32.2 ± 11.9 Elo over 1,762 games at 8+0.08, LLR 2.98, with no time losses. The gain is all speed. Over 2,000 games at a fixed depth of 11, which takes speed out, the SEE build scored −5.7 ± 10.6 Elo, so skipping losing captures does not improve the moves chosen at a given depth, and may cost a little. On 2,178 positions from the SPRT games, each searched with the games' opening budget of 173 ms and a fresh table, it reached the same depth 1.16 times faster: 1.26 times fewer nodes at 8% lower nps. The speedup was 1.42 times in openings, 1.15 in middlegames and 1.04 in endgames. Each extra ply cost about twice the one before, so a 1.16 speedup predicts log 1.16 / log 2 = 0.22 more plies. That matches the 0.19 measured on those positions and the rise from 12.43 to 12.65 plies in the SPRT games. Taken together, the two matches put the speedup's worth at about +38 ± 16 Elo at 8+0.08.
- Search runs on a worker thread; the UCI thread only parses input and requests a stop. Required for `stop` to work mid-search.
- The worker is a `std::jthread`, and stops are sent through its `std::stop_token`, the standard cancellation channel, rather than a hand-rolled atomic flag. A `jthread` stops and joins in its destructor, so no exit path can leave the search running. A default-constructed token never stops, so tests and `bench` call `search` with no thread at all.
- The node limit is checked at every node, so `go nodes` is exact. The clock and the stop request are read every 1024 nodes. Reading the stop token at every node cost about 12% of bench nps; every 1024 nodes it costs nothing measurable, and a stop still lands within about 50 µs.
- An interrupted iteration is discarded, and the result is the last completed one. Depth 1 always completes, so there is always a move to play. A root with no legal move stops after depth 1, since deeper searches cannot change the result.
- `Position::isDraw(ply)` covers the fifty-move rule and repetition, where `ply` is the distance from the search root. If the earlier occurrence is after the root, a second occurrence is already a draw: whichever side steered into the cycle can repeat it again. If the earlier occurrence is the root or before it, the game rule applies and a third occurrence is needed. Ethereal draws the line in the same place, and Stockfish's `StateInfo::repetition` encodes the same split. The scan covers only plies within the halfmove clock, since a capture or pawn move cannot be undone. Within that range it checks only even distances of four or more, because a repeat needs the same side to move and undoing a move takes at least four plies.
- The fifty-move rule ignores the exception for checkmate on the hundredth ply, as Ethereal does. Honouring it needs a legal-move search at every such node, and the case almost never arises.
- Negamax: every score is from the side to move, so one function serves both colours and a child's score is negated on return.
- Fail-soft alpha-beta: a node returns its best score even when that falls outside the window. It costs nothing over fail-hard, and the tighter bounds pay off once the TT and aspiration windows store and reuse them.
- Mate is scored `kMate - ply` for the side delivering it, so the search prefers the fastest mate and, when losing, the slowest. `kMaxPly` (128) bounds the depth, the PV and mate distances.
- The PV is collected bottom-up. Each node passes its children a line, and on a new best move copies the child's line behind that move. No global table is needed, and the line is always the one that produced the score.
- Iterative deepening runs from depth 1 even before anything can interrupt a search. `stop` and time limits will take the move from the last completed iteration, and each shallower iteration costs a small fraction of the next one.

## Evaluation
- v0.2: material only, with the Chess Programming Wiki's Simplified Evaluation Function values (100, 320, 330, 500, 900), scored for the side to move. It exists so the search has something to maximise; PeSTO replaces it in v1.
- v1: tapered material + PeSTO piece-square tables. Public, known-good values; removes tuning from the critical path to Lichess.
- The PeSTO values and tables were generated by script from the C source published on the Chess Programming Wiki, not retyped. A second script checked every number against that source, and checked that `evaluate` matches a port of the published `eval()` on the bench positions, both sides to move. The tables are drawn from White's side with a8 first, as on a diagram, so a White piece looks up `square ^ 56` and a Black piece its own square.
- The score blends a middlegame and an endgame score by phase. Knights and bishops weigh 1, rooks 2 and queens 4, so the starting material is 24 and bare kings are 0. Promotions can push the sum past 24, so it is capped there, as in the published code. Division rounds toward zero, so the score is exactly antisymmetric between the colours, which the mirror test checks.
- The eval is recomputed from the bitboards on every call rather than updated in make/unmake. That keeps `Position` free of eval tables, and NNUE replaces this eval in v2, so incremental code would be thrown away. It costs 43% of bench nps: 5.3M against 9.2M before PeSTO, both pinned to one core. The SPRT plays at a fixed time control, so its result already includes that cost.
- v2: NNUE. HalfKA-style features, one hidden layer, int16 accumulators updated incrementally in make/unmake, SIMD inference. Training data from self-play of the best v1.x build so the net is trained on this engine's own data, not Stockfish's. Trainer in `trainer/` (Python, PyTorch). Nets attached to GitHub Releases, not committed.

## Time management
- v1 plan, superseded by the v1.0 soft and hard limits below: budget `remaining/30 + increment` per move, hard cap `remaining/10`. Stop iterating when the next depth is predicted not to fit.
- v0.2: `timeBudget` returns `min(remaining/30 + increment, remaining/10)`, and the search treats it as a hard limit, since nothing predicts iteration cost yet. remaining/30 assumes about thirty moves are left. The cap matters on a low clock with a large increment, where remaining/30 + increment would spend a quarter or more of what is left. `movestogo` is ignored: for any value up to 30, remaining/30 is at least as cautious as dividing evenly.
- Only the side to move's clock is read; the other is validated and ignored. Given both a clock and `movetime`, the shorter limit wins, as in Stockfish. There is no move-overhead allowance yet. The cap leaves a margin, and lag handling belongs to the v1 work, measured against Lichess. (Superseded: v1.0 needs none; see below.)
- v1.0: two limits. The budget is still `min(remaining/30 + increment, remaining/10)`. The soft limit is half of it and is checked only between iterations: once it has passed, no new depth starts. The hard limit is `remaining/10`. It is checked every 1024 nodes and stops the search mid-iteration, discarding that iteration. Stockfish's optimum and maximum times split the work the same way.
- Half, because the next depth usually costs more than all the earlier ones together, so one started past half the budget would end beyond it. This common rule of thumb is the planned prediction with a fixed growth factor of 2, so nothing is measured per position. The price: an iteration started just before the soft limit can still run into the hard limit and be thrown away.
- A first version put the soft limit at the full budget and failed SPRT at -21 Elo. Iterations in progress ran on towards the hard limit: in the first 20 plies it spent 512 ms a move against the baseline's 312 ms, for 0.3 more depth, and from ply 40 on it had less time and searched shallower than the baseline.
- `movetime` sets only the hard limit, so the search uses all of it, as before.
- The engine has no move-overhead allowance, because lichess-bot already provides one. It subtracts its own processing time and its `move_overhead` setting (2000 ms by default) from the side to move's clock before sending `go`, so the engine never sees time it cannot spend. fastchess passes the true clock, and no SPRT game has been lost on time.

## UCI and Lichess
- `uci`, `isready`, `ucinewgame`, `position`, `go` (`wtime btime winc binc movetime depth nodes infinite`), `stop`, `quit`. Extensions: `bench`, `perft <depth>` (divide output).
- Command-line arguments are joined and run as a single command, after which the engine exits, as Stockfish does. Testing tools such as OpenBench call `engine bench` this way, and `zugzwang perft 5` works too.
- Every output line is flushed. lichess-bot reads through a pipe, which buffers by block, so an unflushed `uciok` would never arrive. Every write also takes one mutex, because the search thread prints `info` and `bestmove` while the UCI thread answers `isready`.
- `go` values must be positive integers, except clocks and increments, which may be zero (`winc 0` is how lichess-bot reports no increment). `depth` is capped at `kMaxPly`, and parameters the engine does not use are ignored. A `go` with no limit is treated as `go infinite`. `go infinite` holds `bestmove` until `stop` even if the search ends first, as UCI requires; the worker waits on a `condition_variable_any` with the stop token. With no legal move the answer is `bestmove 0000`, the UCI null move.
- `info` lines carry depth, score, nodes, nps, time and the PV. Mate scores are given in moves, negative when the side to move is being mated, as UCI specifies.
- `go`, `perft`, `bench` and `quit` stop a running search first. `position` during a search changes only the UCI thread's position, since the search works on its own copy. `ucinewgame` has nothing to reset until the TT exists, so it is ignored like any unknown command. (Superseded in v1.x: `ucinewgame` now also stops a running search first, then clears the transposition table.)
- At end of input, a limited search runs to completion and an infinite one is stopped. Stockfish treats end of input as `quit`. Letting a limited search finish keeps `echo "go depth 6" | zugzwang` and the in-process tests deterministic, and an infinite search could never end otherwise.
- The command loop takes streams rather than `std::cin` and `std::cout`, so tests drive it in-process. It starts in v0.1 with `position`, `perft` and `quit`, because debugging perft needs `position` to reach the failing line.
- `position` builds a separate `Position` and swaps it in only if the FEN and every move are valid, so a bad command leaves the current position untouched. Move text is matched against `generateMoves` output, since `make` trusts its input.
- `perft` makes every move, including the last ply. Bulk counting the final ply needs a legal move list, and generation here is pseudo-legal. Its depth is capped at 64, because it recurses once per ply and an unbounded depth overflows the stack.
- The official lichess-bot Python bridge connects the binary to Lichess. A hand-written bridge signals nothing; the official one already handles the Bot API, challenges and clocks.
- lichess-bot runs a copy of the release binary in `lichess-bot/engines/`, not `build/zugzwang`, so rebuilding during v1.x work never swaps the engine between games.
- The bot is hosted from the PC by default, sometimes the laptop, never both at once: two lichess-bot copies on one account would both accept the same challenges. Each machine has its own `bot:play` token, so either can be revoked alone, and builds its own engine, since a `-march=native` binary may crash on another CPU. On Windows the engine `name` in `config.yml` is `zugzwang.exe`.
- Besides the token and engine path, two settings differ from lichess-bot's default `config.yml`. `ponder` is off, because the engine has no `go ponder` or `ponderhit` and would send `bestmove` on the opponent's time. The default `uci_options` are deleted, because the engine declares no options and lichess-bot closes it when told to set an undeclared one. `move_overhead` keeps its default; see Time management. The default variants list is standard only, which the engine needs, since it has no Chess960 castling.

## Measuring strength
- `bench`: fixed positions at fixed depth, prints total nodes and nps. The node count is a fingerprint — it changes iff search or eval behaviour changed.
- On the development laptop, bench nps for the same binary varies about 2× with thermal state and with which core the run lands on. Speed comparisons therefore pin both binaries to one core with `taskset -c 1` and interleave their runs. Logged nps from v1.0 PeSTO onwards is pinned; earlier rows are not.
- The bench set is ten positions: the start position and the five other perft suite positions for tactics, castling and promotions, two common openings, a Lucena rook endgame and Fine #70, a pawn endgame. The endgames add few nodes today, but they will exercise the TT and endgame eval once those exist. Depth 5 took about a fifth of a second in Release at v1.0, so it could run on every change. The depth goes up as the search gets cheaper per ply, and each raise is a logged bench change. At v1.0, depth 6 would have taken 1.4 s and depth 7 8.5 s, pinned, so the raise waited for the TT and pruning.
- After LMR the bench depth went from 5 to 11. Depth 5 took 17 ms, too short for nps to repeat, and it fingerprinted little of the selective search: every null search dropped straight into quiescence, and LMR reduced by at most two plies. Pinned on the PC, depth 9 took 0.4 s with nps varying 18% between runs, depth 10 0.8 s, depth 11 1.9 s and depth 12 4.0 s; from depth 10, nps repeated within 2%. Depth 11 keeps the bench at a couple of seconds, and it gets cheaper as the search improves. The Debug build, which CI also runs, took 22 s without sanitizers on the PC, against a 20-minute job limit.
- Every log row in `docs/ROADMAP.md` names the machine it ran on, `PC` or `laptop`. The engine searches on one thread, so nps, Lichess rating and time-limited SPRT results all depend on the CPU, and the bot may be hosted on either machine. Bench node counts do not depend on it, which makes the bench a portability check: a build on a new machine must reproduce the logged count.
- CI runs `bench` in both builds and checks the output format. Release and Debug give the same node count, so the search does not depend on optimisation level, and the Debug run puts the whole search under the sanitizers.
- SPRT with fastchess at 8+0.08 against the previous accepted build. Lichess rating is the public scoreboard, not the development signal.
- SPRT starts in v1.0, which supersedes the plan to start it in v1.1. Quiescence, MVV-LVA, PeSTO and time management each aim to change playing strength. Bench only shows that the search changed, not that it plays better, and a feature that looks right but loses games fails its SPRT.
- The book is `noob_3moves.epd` from the official Stockfish books repository: 150,932 balanced positions three moves in, saved as `tools/book.epd` (gitignored). UHO books start from deliberately unbalanced positions to cut the draw rate between strong engines. This engine rarely draws, so a balanced book is simpler until its draw rate climbs. Every book position parses in `fromFen`, which was checked, so no game can start from a rejected position.
- Each opening is played twice with colours swapped, so an opening's bias cancels within the pair. fastchess plays two games per round by default; `-repeat` states it explicitly.
- Bounds are [0, 5] normalized Elo with alpha = beta = 0.05: H0 is no gain, H1 a gain of 5. Normalized Elo is fastchess's default model, and the command names it so the units are explicit. Large early gains pass within a few hundred games.
- The baseline is the last accepted build, kept in `baseline/` (gitignored). After a passing change is committed, its build replaces the baseline. Each run's games go to `sprt/last.pgn` for inspecting losses. fastchess also autosaves its state as `config.json` in the working directory so a run can resume, so `-config outname` moves that file into the ignored `sprt/` too.
- fastchess is v1.8.2-alpha, built from source and installed to `~/.local/bin`. Every fastchess release carries the alpha suffix.
- The setup was checked with 200 games of v0.2 against itself, using the `/sprt` command capped at 100 rounds. All games ended by mate or a draw rule, with no time losses, illegal moves or crashes, so the time budget holds at 8+0.08. The result was +8.7 ± 31.8 Elo, consistent with zero, which is the expected outcome for identical engines.
